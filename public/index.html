AI Operation Manager

A zero-dependency Python CLI that installs and manages versioned AI skills — slash commands, agents, hooks — across all your projects. Skills are versioned by git tag; each project independently pins the versions it needs.

✓ Zero dependencies Python 3.10+ Multi-agent MIT License

Key Highlights

🏷️

Git-backed versioning

Skills live in a remote git repo tagged with semantic versions (e.g. skills/create-jira-story@1.0.0)

📌

Per-project pinning

Projects declare requirements in their AI agent config file. Different projects pin different versions simultaneously.

🤖

Multi-agent support

Works with Claude Code, Codex, Kiro, Cursor, OpenCode, and Aider — each with its own directory layout.

📦

Zero runtime deps

Pure Python stdlib only. No pip install needed when using source mode. Requires only git on PATH.

Getting Started

Installation

Download the latest binary for your platform from the Releases page, then run aom deploy to install system-wide:

PlatformFile
Linux (x86-64)aom-linux-amd64
Windows (x86-64)aom-windows-amd64.exe
bash
$ chmod +x aom-linux-amd64
$ ./aom-linux-amd64 deploy
→ Deployed to ~/.local/bin/aom and added to PATH
PowerShell
PS> .\aom-windows-amd64.exe deploy
→ Deployed to %LOCALAPPDATA%\ai-operation-manager\bin\aom.exe

After deploying, open a new terminal and verify:

terminal
$ aom --help

Copy the binary manually to a directory on your PATH:

bash
# Linux / macOS
$ chmod +x aom-linux-amd64
$ sudo mv aom-linux-amd64 /usr/local/bin/aom
PowerShell
# Windows — copy to any directory on your PATH
PS> Move-Item aom-windows-amd64.exe C:\tools\aom.exe

Clone the repository and install in editable mode:

bash
$ git clone git@github.com:yourorg/ai-operation-manager.git ~/aom
$ cd ~/aom && python -m venv .venv
$ source .venv/bin/activate
$ pip install -e ".[dev]"
$ python -m aom --help
ℹ️

Add export PATH="$HOME/aom/bin:$PATH" to your shell profile to use the aom command directly from source.

Quick Start

Three steps to get up and running on a new project:

Initialize the project

Run aom init from your project root. The wizard detects your AI agent config file, asks for remote repo URLs, and optionally fetches the tag index.

aom init
$ aom init
Directory: /home/user/my-project
Found: CLAUDE.md → ClaudeCode
Use this config file? [Y/n]:
Repository URL(s): git@gitlab.com:myorg/ai-grimoire.git
✓ Saved 1 repository URL(s) to settings.json
✓ git@gitlab.com:myorg/ai-grimoire.git — 12 skill version(s)

Install skills (they are saved to config automatically)

Use aom install to add skills — the requirement is saved to aom.json automatically (like npm):

aom install
$ aom install create-jira-story:1.0.0
$ aom install design-workflow:>=1.1.0
$ aom install evaluate-workflow

Or edit aom.json directly:

json · aom.json (required section)
{
  "required": {
    "create-jira-story": "1.0.0",
    "design-workflow": ">=1.1.0",
    "evaluate-workflow": "latest"
  }
}

Install everything

Run aom sync — it reads the requirements and installs all missing skills. Any teammate cloning the project runs the same command.

terminal
$ aom sync
✓ create-jira-story@1.0.0 → [local:ClaudeCode]
✓ design-workflow@1.1.0 → [local:ClaudeCode]
✓ evaluate-workflow@2.0.0 → [local:ClaudeCode]

aom init

Interactive setup wizard. Runs in two phases: Phase A creates or updates global settings (repositories, local paths) — on first run it prompts for everything; on subsequent runs it confirms or updates existing values. Phase B detects AI agent config files in the project, lets you choose agents, and writes aom.json to the project root.

aom init
$ aom init
Project : /home/user/my-project
Global settings not found. Setting up global configuration.
Repository URL(s): git@gitlab.com:myorg/ai-grimoire.git
✓ Global configuration created: ~/.config/aom/settings.json
Found: CLAUDE.md → ClaudeCode
Use this agent? [Y/n]:
✓ Project configuration saved to aom.json
✓ Fetched. 17 total skill version(s) available.

aom init writes configuration to aom.json at the project root:

json · aom.json
{
  "version": 2,
  "agents": ["ClaudeCode", "Codex"],
  "required": {}
}

aom install

Installs an operation into the target scope and saves the requirement to aom.json (or global settings with --global), similar to how npm install saves to package.json. Requires aom init to have been run first.

aom install examples
# Latest stable, local scope
$ aom install create-jira-story
# Exact version, local scope
$ aom install create-jira-story:1.0.0
# Minimum version, global scope
$ aom install design-workflow:>=1.0.0 --global
# Skip if already installed
$ aom install create-jira-story --no-overwrite
# Refresh tag index before installing
$ aom install create-jira-story --fetch
💡

With multiple selected agents, install runs against each one and prints scope labels like [local:Codex], [local:ClaudeCode].

aom sync

Reads requirements from aom.json and installs missing or outdated operations for all selected agents. Falls back to agent config files if no requirements are in the config.

aom sync
# Default: install from requirements
$ aom sync
# Preview without installing
$ aom sync --dry-run
# Fetch latest tags first, then sync
$ aom sync --fetch
# Sync + remove local extras not in config
$ aom sync clean
# Replicate one agent's config/content to others
$ aom sync agents

Configuration

Local Config File (aom.json)

aom init creates an aom.json file at the project root. This is the single source of truth for local configuration. Skills are added via aom install (like npm) and removed via aom remove.

Local config (aom.json)

Project-specific configuration:

json · aom.json
{
  "version": 2,
  "agents": ["ClaudeCode", "Codex"],
  "required": {
    "create-jira-story": "1.0.0",
    "design-workflow": ">=1.0.0",
    "evaluate-workflow": "latest"
  }
}

Global settings (aom init)

Shared across all projects:

json · settings.json
{
  "version": 3,
  "agents": ["ClaudeCode", "Codex"],
  "repositories": [
    { "url": "git@gitlab.com:myorg/ai-grimoire.git" }
  ],
  "local_paths": ["/home/user/my-local-skills"],
  "required": {},
  "initialized_paths": ["/home/user/my-project"]
}
ℹ️

Config files are versioned and backward compatible. New fields have sensible defaults so older configs are transparently upgraded on read.

Version Constraints

Three syntaxes are supported for pinning skill versions:

SyntaxMeaningExample
1.0.0 Exact version — installs precisely this version create-jira-story: "1.0.0"
>=1.2.0 Minimum version — installs the highest satisfying version design-workflow: ">=1.1.0"
latest or * Highest stable version — pre-releases excluded evaluate-workflow: "latest"
⚠️

Pre-release versions (e.g. 1.2.0-SNAPSHOT) are never selected by latest or *. Use an exact version constraint to install pre-releases.

Global Settings

Global settings are created and updated by aom init and stored at a platform-specific location:

PlatformSettings file
Linux / macOS~/.config/aom/settings.json
Windows%APPDATA%\aom\settings.json
 
json · settings.json
{
  "version": 3,
  "agents": ["ClaudeCode", "Codex"],
  "repositories": [
    { "url": "git@gitlab.com:myorg/ai-grimoire.git" },
    { "url": "git@github.com:myorg/more-skills.git" }
  ],
  "local_paths": ["/home/user/my-local-skills"],
  "required": {},
  "initialized_paths": ["/home/user/my-project"],
  "fetch_ttl_seconds": 3600
}

yaml · Project A — CLAUDE.md

  create-jira-story: "1.0.0"

Installation Scopes

Local scope

Location: <project>/<agent-dir>/

Project-specific skills pinned via aom sync. Committed to the project repo (or .gitignored).

Global scope

Location: ~/<agent-dir>/

Available in all projects. Install with --global. Local takes precedence when both exist.

Key Module Responsibilities

ModuleResponsibility
cli.pyArgument parsing and command dispatch (init, install, list, sync, remove, update, env, fetch)
config.pyAgent detection via AGENT_MAP, path resolution for global/local dirs
models.pyVersion (semver with prerelease), SkillRecord, VersionRequirement dataclasses
git.pyGitRepo: bare clone management, tag listing, lazy blob extraction
discovery.pyFilesystem scanning with adapter chain + git repository scanning
manifest.pyParses Skills Requirements and Skills Source YAML blocks from config files
settings.pyGlobal user settings JSON persistence (XDG on Linux, %APPDATA% on Windows)
resolver.pyMatches version constraints (exact, >=, latest, *) against discovered SkillRecords
installer.pyExtracts blobs from git or copies local files into the target scope directory
registry.pyJSON registry tracks what's installed per scope

Adapter Pattern

Three structure adapters detect how skills are laid out on disk. They're tried in priority order via an adapter chain in discovery.py:

AdapterOn-disk layoutNotes
SuffixAdaptername@1.0.0/Version in dir name; requires renaming on release
DirAdaptername/1.0.0/Multiple versions coexist; deeper nesting
MetadataAdapterversion in frontmatterRecommended — stable paths, version co-located with definition

Registry Format

Stored inside the agent directory as registry.json:

json · .claude/registry.json
{
  "version": 1,
  "installed": {
    "skills/complex-evaluator": "1.0.2",
    "commands/deploy-skills": "1.0.0"
  },
  "updated_at": "2026-03-27T12:00:00+00:00"
}

Git Tag Convention

Skills repositories use structured tags to version each skill independently:

git tags
skills/create-jira-story@1.0.0
skills/design-workflow@1.0.0
commands/deploy-skills@2.0.0
agents/my-agent@1.0.0

The GitRepo class maintains a local bare clone using --filter=blob:none (no file contents downloaded upfront). Blobs are fetched lazily when a skill is actually installed.

Auto Version Bumping

When a PR is merged to main, the bump-version workflow automatically creates a new version tag based on the PR title:

PR title patternBump typeExample
feat: ... or feat(scope): ...Minorv1.0.0 → v1.1.0
type!: ... or BREAKING CHANGE in bodyMajorv1.0.0 → v2.0.0
Anything else (fix:, chore:, docs:)Patchv1.0.0 → v1.0.1

Releasing

create a release
$ git tag v1.2.0
$ git push origin v1.2.0
→ GitHub Actions creates a release with Linux + Windows binaries
→ SHA-256 checksums are auto-generated and attached
💡

Tags containing a hyphen (e.g. v1.2.0-beta) are automatically marked as pre-releases.

Versioning Skills in a Remote Repository

Skills are versioned with git tags. Every time a skill's frontmatter version is bumped, a matching tag must be pushed for it to be installable:

release a new skill version
# 1. Bump version in frontmatter
# skills/create-jira-story/SKILL.md: version: 1.3.0
$ git add skills/create-jira-story/SKILL.md
$ git commit -m "Bump create-jira-story to 1.3.0"
# 2. Tag the commit — REQUIRED for installability
$ git tag skills/create-jira-story@1.3.0
$ git push && git push --tags
⚠️

If the tag is omitted, the version exists in the frontmatter but cannot be resolved or installed by aom.

Different skills have independent tag histories — each skill's versions are tracked separately:

git log --oneline
Commit A ← tag: skills/create-jira-story@1.0.0
← tag: skills/design-workflow@1.0.0
Commit B ← tag: skills/design-workflow@1.1.0
Commit C ← tag: skills/create-jira-story@1.1.0
Commit D ← tag: skills/create-jira-story@1.2.0 (HEAD)
